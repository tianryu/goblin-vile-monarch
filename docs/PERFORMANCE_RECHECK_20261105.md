# 11 月 5 日性能与音频复查

用户报告在 TapTap 小游戏内，鸿蒙 Mate70、红米 K30、华为麦芒三台手机第一天转身行走就出现掉帧。问题不限于第六天。当前无上述手机的远程性能采集，以下是源码定位和本机桌面测量，不能替代这些设备的宿主复测。

## 已实施的定向优化

- Painter 只在位置、缩放或角度变化时调用 Cocos 变换接口。引擎的相应 setter 会使变换失效，即使提交相同的值也会产生后续工作。固定图层计数改为数组，减少每张精灵的重复 Map 查询。
- 奔跑按钮的按下缩放交给 Painter 一次提交，消除绘制时先恢复原尺寸、再缩小按钮的往返更新。
- 陆地遮罩按洞口至海岸的固定世界范围绘制。镜头只移动遮罩位置，取消镜头移动时反复改变遮罩大小与锚点。
- 离屏的余火、命中等装饰不再生成图形顶点。相距很近的重叠余火共用火舌，原模型的伤害和生命周期各自继续结算。火焰三层颜色复用，取消每层创建三份颜色再挑一份。

静止场景暂停世界时，两个实际构建各绘制 30 帧，旧版有 5010 次 setScale、5490 次 setPosition，新版分别为 0、30。这个统计仅说明重复提交减少，不等于行走中所有位置提交都可省略。证据在 `qa/cocos/performance-20261105/transform-counts.json`。

## 桌面对照

环境为 Windows Edge 156、Intel UHD Graphics、ANGLE Direct3D11，横屏视口 844×390、DPR 2，实际画布 1688×780。逻辑按 30 Hz 更新，游戏渲染目标 60 FPS。测试使用独立 QA 存档、种子 731，密集场景提高双方耐久维持兵力，属于压力夹具。

旧版为 hero-motion-20261105，新版为 performance-20261105。两版依次采样开局 12 秒、第六天转向 25 秒、24 友军对 96 敌军的第三十天战斗 30 秒、复活后恢复相同兵力的转向 25 秒、交互目标循环 55 秒。复活场景人为恢复战场负载，便于比较，不能当作正常复活后的兵力事实。

| 场景 | 旧版画面组装 P95 | 新版画面组装 P95 | 新版游戏帧率 | 新版帧间隔 P95 | 新版最长帧间隔 |
| --- | --- | --- | --- | --- | --- |
| 开局 | 0.60 ms | 0.60 ms | 60.1 | 19.4 ms | 20.6 ms |
| 第六天反复转向 | 0.90 ms | 0.80 ms | 59.9 | 19.3 ms | 39.5 ms |
| 第三十天密集攻城 | 1.70 ms | 1.10 ms | 59.8 | 19.4 ms | 84.6 ms |
| 复活后同负载转向 | 1.60 ms | 1.30 ms | 59.3 | 19.4 ms | 54.5 ms |
| 往返交互目标 | 0.60 ms | 0.80 ms | 60.0 | 19.2 ms | 22.8 ms |

画面组装只计 GameView.render 的 JS 耗时，不包含全部引擎提交和 GPU 开销。密集战斗的组装下降约 35%，交互目标循环没有稳定改善。密集战斗与复活场景各有一次超过 50 ms 的长帧，不能报告为全程无卡顿。

额外在同一浏览器做 4 倍 CPU 降速的第一天测试。反复转向各 25 秒，旧版约 60.0 FPS、组装 P95 2.7 ms，新版约 59.9 FPS、组装 P95 3.6 ms。新版有一次 66.6 ms 长帧，未显示稳定的整体帧率改善。CPU 降速是桌面诊断方式，不代表上述任何一台手机。

采集过程使用 CPU 采样器与定向计时，存在观测开销。早期 before/report.json 的 fps 字段记录了浏览器 requestAnimationFrame 约 165 Hz，不能当作游戏帧率。旧版游戏帧率应由 timings.render.count / wallMs 计算，修订后的测试器已分别保存 rafFps、游戏 fps 和游戏帧间隔。

## 内存与剩余风险

新版五场结束后主动 GC 的 JS 堆约 14.6、16.4、17.4、17.5、16.6 MiB。交互往返后回落，没有在本次短测里发现持续增长的 JS 堆泄漏。Cocos 纹理记账约 105.8 至 124.9 MiB，仍有移动端驻留压力。这些数值不能相加作为手机进程内存，也不能排除 TapTap 宿主、音频或图像解码的设备专属问题。

第一天频繁转向导致三台实机掉帧仍标记为待真机复测，根因尚未由设备采样证实。本次已削减明确存在的重复工作，未将桌面结果写成手机修复成功。

## 音频

- 主菜单保持静音。在开始、继续的实际操作回调内以零音量预启音源，菜单退场后渐入游戏音景。返回主菜单时暂停音景。
- 若已请求的循环音源没有实际播放，每 1.5 秒至多重试一次，供首次播放失败或系统中断后的恢复使用。
- 白天配乐增益从 0.11 到 0.18，傍晚配乐从 0.095 到 0.15。自然声公共系数从 0.6 到 0.9。鞭声增益从 0.24 到 0.36。这些是播放参数，不能当作感知响度的精确百分比。
- 桌面真实触控验证主菜单静音、开始播放、返回主菜单静音、继续播放。音效可听程度仍需设备扬声器和耳机试听。

TapTap 官方 InnerAudioContext 文档支持 autoplay，并给出自动播放例子，未查到所有小游戏统一要求先点击的规定。Cocos 3.8 AudioSource 的本地源码说明 Web 平台存在首次自动播放限制，可在 TOUCH_END/MOUSE_UP 回调触发或等待下一次交互解锁。实际宿主后端与浏览器应分别检查。

参考 [TapTap 音频属性](https://developer.taptap.cn/minigameapidoc/dev/api/media/audio/InnerAudioContext/)、[音频上下文与释放](https://developer.taptap.cn/minigameapidoc/dev/api/media/audio/tap.createInnerAudioContext/)、[运行时优化建议](https://developer.taptap.cn/minigameapidoc/dev/tutorial/performance/runtime/runtime-suggestions/)。

## 验证与交付

TypeScript、Creator 两种构建、桌面渲染与触控、播放状态、静止变换提交、离屏特效、重叠火焰和转向画布稳定性检查通过，测试中没有脚本错误或资源请求失败。原始记录、CPU profile、失败夹具日志和截图在 `qa/cocos/performance-20261105`。

TapTap 本地交付为 `release/taptap-20261105-r3/game.zip`，版本 0.10.3。新版另开本地试玩端口 `http://127.0.0.1:42831/?build=performance-20261105`，浏览器存档按端口隔离。未进行平台上传、发布或实体设备验证。
